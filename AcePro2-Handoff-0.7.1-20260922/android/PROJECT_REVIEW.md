# 项目审阅与触发替代方案

审阅日期：2026-09-22。当前 App：0.7.1，Android Camera SDK 2.2.0。

## 结论

现有项目已完成前台手动触发的无线图片传输原型，并非完整的相机按键触发产品。不能通过给现有 WORKING 回调加计时器来识别长按：短按与长按的独立测试均只有 WORKING / PHOTO_NORMAL，计时值来自监听启动，而非物理按键按下。

优先建议验证「机身普通拍照 → 获取新增 JPG → 手机热点传电脑 → agent」。它不要求预览流，旧项目已有下载实现可参考，适合当前镜片分析需求；它仍会响应短按，不等同于实现了相机长按。

若必须保留“按住一个实体按钮才分析”的交互，应验证连接手机的独立 BLE 按钮/可报告按下松开的 HID 按钮。按钮可以装在相机支架上，但不是读取影石机身快门。具体设备的事件能力须实测，不应默认所有蓝牙自拍器都报告长按。

## 范围与验证

- 阅读当前 Android 会话、解码/组帧、预览比例、PixelCopy、批次采集、上传、单帧分析预留接口、生命周期与 Manifest/构建配置。
- 阅读电脑 receiver.py、chunk_upload.py 和全部现有测试。
- 核对旧 vertical-demo 的拍摄回调、自动下载和文件队列。
- 核对本机 Android SDK 的公共接口、桌面 SDK 2.2.0 头文件，以及官方 API/操作说明。
- 离线编译成功；11 项 Android 单元测试、8 项 Python 测试通过。
- 另外在临时目录、独立内存状态中复现了下述上传槽位耗尽、重启后重复落盘、hook 失败后重复落盘。未改动现场批次和正在运行的程序。
- 之前真机验证的两批 10 张图片均解码成功；本轮审阅未宣称新增触发方式已通过实机测试。
- 没有做大范围运行代码重构，本文件是审阅结果。

## 需要处理的问题（按当前影响排列）

### 1. P1／目标缺口：监听、采集、待机还没有形成同一流程

位置：MainActivity.kt:92、117、161；CameraSession.kt:128、214 附近。

监听模式直接拒绝采集；采集结束 stopAndWait 会注销监听、disconnect、release；切后台或锁屏也会停止任务。现在即使把 WORKING 回调接到 triggerBatch，也会被 monitoring 守卫拒绝。去掉这一行仍不足以工作：start() 对已有会话直接返回，而监听模式没有预览，因此会等不到渲染帧。

改法：把“控制连接”“拍摄事件监听”“预览流”拆成独立状态。保留控制连接等候事件，仅在需要时启动/停止预览，或直接下载新照片。决定前台常亮还是前台服务待机；后者是新增开发，不是已有能力。相机网络和热点上传路由也需独立管理，不能简单把目前整次断开改成不执行，否则进程仍绑定相机网络，可能再次破坏热点上传。

### 2. P2／已复现：4 次未完成上传会阻塞后续新批次

位置：desktop/chunk_upload.py:20、33；MainActivity.kt:106。

每次重拍都会生成新 requestId，放弃的分块上传仍占一个 slot。连续 4 次中途取消/断网后，第 5 批得到 too many pending uploads；旧批次需闲置 15 分钟才在下一请求中清理。手机没有 abort 接口，也没有重试 lastBatch 的按钮。

隔离复现：向 4 个不同 uploadId 各发送 1 字节、声明总长 100 字节；第 5 个合法 uploadId 被拒绝。

改法：本地保存待发送批次，允许沿用 requestId 重传；增加 abort/状态查询，给放弃任务及时释放空间。不要用无界增大 slot 数掩盖问题。

### 3. P2／已复现：去重不持久，重启或发布失败会重复落盘

位置：desktop/chunk_upload.py:54；desktop/receiver.py:127。

完成结果只缓存于内存；save_batch 每次创建随机目录。接收端重启后重放同一 uploadId 和同一内容会产生第二个目录。另一个路径是保存成功、on_batch 后续失败：成功状态尚未记录，重试 commit 会再保存并再次调用 hook。

隔离复现：相同请求分别经过两个 Uploads 实例得到 2 个目录；首次 publish 落盘后模拟 OSError，重试 commit 也得到 2 个目录。

改法：以 requestId + 内容哈希持久化唯一任务。先原子落盘及记录接收状态，再单独入 agent 队列；请求重放返回原任务状态。同一 ID 不同内容必须拒绝。当前 on_batch 只有 print，没有真的调用模型；真正接入后重复触发会变成重复推理及费用。

### 4. P2／已确认：采集图像尺寸与手机界面布局耦合

位置：analysis/SceneSampler.kt:56；AspectPreview.kt 的 onMeasure。

JPEG 的目标尺寸取自 SurfaceView 的屏幕尺寸，而不是视频有效分辨率。此前图片为 970×546；这证明输出不是固定 1280 像素长边。增加按钮、旋转屏幕、弹键盘、较小屏幕都会进一步改变可用尺寸。现有等比逻辑是正确的，但细小点光源、反光边缘等模型证据会受分辨率影响。

改法：优先采用相机照片；保留预览抽帧时改为与 UI 独立的取图尺寸/解码输出，并继续保留完整比例。需要设定最小可分析分辨率；不能用放大低分辨率截图冒充新增细节。

### 5. P2／已确认：本地采集成功后不能独立重发

位置：MainActivity.kt:106、115、129。

lastBatch 保存了整批图片，但没有任何读取/重新提交入口。上传失败后用户只能再次采集，新场景可能已经改变，原批次也会在新任务开始时被清空。所谓“续传”目前只限同一次 submit 内部的重试，并非关闭 App 或任务失败后的恢复。

改法：将采集和上传拆成两步状态，批次落到手机缓存目录；提供重发/丢弃，并保存 manifest 与 requestId。对当前场景分析另加有效期，过时批次应提示过时而不能伪称当前画面。

### 6. P2／接入限制：agent hook 同步运行且被全局上传锁包住

位置：desktop/receiver.py:127–134。

on_batch 当前只打印，这是明确的占位接口；还没有 agent 推理、任务状态或结果回手机。直接在这里加入几十秒的模型调用，会占住 UPLOAD_LOCK，阻塞其他分块。手机读超时仅 5 秒，会重试 commit，放大发布问题。

改法：接收端返回“已持久化接收”的任务 ID；后台独立 worker 调 agent；App 查询任务结果或订阅结果。区分 received / analyzing / completed / failed，不把 HTTP 200 接收回执当成模型分析完成。

## 已有实现值得保留的部分

- 相机 Wi-Fi → 手机；手机个人热点 → 电脑的两段无线拓扑已实测成功。相机热点双客户端传输在现场出现重传与建连失败，但尚不能断言所有 Ace Pro 2 都有该问题或定位到具体固件缺陷。
- Annex-B 组帧、关键帧恢复、有界队列、后台 JPEG 压缩、传输分块确认及 SHA-256 完整性检查。
- 预览等比显示，不主动改变相机拍摄模式/录像参数；不把长按预留枚举伪装成实机支持。
- 接收端限制解压总量、条目和文件名；敏感 Maven 配置使用忽略的 local.properties。

仍是局域网调试服务：没有鉴权且绑定所有接口，不能作为公网 agent 接口直接部署。这里只作为部署边界记录，不影响现有受信任热点联调。

## 替代触发方式

| 方案 | 当前证据 | 是否独立识别长按 | 建议 |
| --- | --- | --- | --- |
| 相机普通拍照事件 → 下载新增 JPG | 已实测 WORKING；SDK 有列表/下载 API，旧项目也有代码 | 否，短按也会触发 | 优先验证，完全不需要预览流 |
| 手机音量键长按 | Android 有按键/长按接口，当前 App 尚未实现 | 可在手机前台实现，需实测按键跟踪 | 无需额外硬件，但按钮在手机上 |
| 独立 BLE / HID 按钮连接手机 | 可设计按下/松开通知；未测试具体设备 | 取决于设备是否报告完整事件 | 想把触发按钮放相机旁时验证 |
| 相机连续两次拍照作为口令 | 可以尝试统计两个独立拍照事件；尚未测试忙碌时第二按是否丢失 | 是“双次拍照”，不是长按 | 会多拍一张，需防连拍/初始化误判，不优先 |
| 相机 V 手势/语音拍照 → 同一照片流程 | 官方支持 V 手势 3 秒倒计时拍照；回调来源不能区分 | 否 | 适合免手持场景，须验证 SDK 会话共存 |
| 原机身快门只在长按时触发 | 当前两次测试事件相同，无按下/松开公共回调 | 目前没有证据支持 | 向影石申请按键扩展/定制固件能力 |

SDK 内部或桌面头文件中的 shutter speed 指曝光时间，不是快门按键；本次检查没有发现更换 Linux SDK 就能取得物理长按的依据。反射私有方法、按拍摄完成耗时猜长按，都不应作为可靠实现。

## 旧项目可复用点与陷阱

vertical-demo/app/src/main/java/com/insta/vertical/demo/ui/capture/CaptureParamsViewModel.kt:498 已有 onCaptureFinish → JPG 下载 → 上传流程。文件管理页有串行下载队列与重复入队检查。

但不应直接照搬两点：

1. 当前 Ace Pro 2 实测只观察到 WORKING，不能把 FINISH 一定到达作为唯一条件；需验证完成事件或用 isWorking + 新文件差异检测作有界补偿。
2. 旧代码 :525 左右在路径缺失时 listMediaFiles().lastOrNull(JPG)，未验证列表排序，也未与触发前文件集比较，可能上传旧照片。应记录基线、识别新增文件、等待文件就绪，再下载；不能用“最后一张”代替身份判断。

## 建议实施顺序

1. 先做单次机身拍照 → 新增 JPG 下载实测，保留现有十帧通道用于对照。
2. 拆分控制会话和取图流程，建立等待 → 取图 → 待发送 → 已接收的状态机，避免丢失后续触发。
3. 修复未完成上传清理与持久化幂等，再对接 agent 队列。
4. 镜片分析先比较一张清晰照片与少量不同画面，不假设十张近似图一定更好；保留可调数量，按识别效果及响应时间选择。
5. 若产品坚持长按，再验证手机按键或独立按钮。厂商确认前不宣称原机身快门长按已支持。
